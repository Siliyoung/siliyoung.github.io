如何使自己具有“前瞻性”,从被动信息获取到构建自己的技术雷达

2026 年 08 月 20 日·8 min read
ON THIS PAGE
  1. 先改变一个观念：不要追工具，追“问题”
  2. 建议建立自己的“技术雷达”
  3. 信息源也不要靠“等别人告诉你”
  4. 学习方式应该从“开始学”转到“开始做“

感觉目前依赖的是一种被动的信息获取方式

别人用了一个好工具 → 告诉你 → 你才知道 → 然后发现别人已经用了很久

真正有“前瞻性”的人，并不是每天知道最多新工具的人，而是慢慢建立了一套自己的技术雷达（Technology Radar）：知道去哪里发现变化，怎么判断哪些变化重要，以及怎么快速试用。

而且现在这个问题比几年前更明显。GitHub 的 2025 数据显示，AI/Agent 已经开始改变开发者使用的语言、工具乃至整个开发流程；例如 TypeScript 在 2025 年首次成为 GitHub 上使用最广的语言，而 AI 相关项目和 Agent 工作流增长非常快。所以会感觉“东西越来越多”，不是错觉。

先改变一个观念：不要追工具，追“问题”

比如看到：

如果逐个追，会永远追不完。

但换一个视角，它们其实属于几个稳定很多的问题：

前瞻性来自掌握这张地图，而不是背地图上的品牌

所以以后有人跟你说：

“最近 X 特别好用。”

你的第一反应不要是：

“完了，我又不知道。”

而应该是：

“X 在整个软件开发链路中解决哪个问题？”

只要这个问题能回答出来，你其实已经抓住 70% 了。

建议建立自己的“技术雷达”

可以只维护 4 个区域：

区域 意思 例子
Adopt 已经在用 Git、Docker、Postgres
Trial 正在认真尝试 Claude Code、某个框架
Assess 值得关注 MCP、Agent frameworks
Ignore 暂时不管 与自己方向无关的技术

关键在最后一个：Ignore。

很多人最容易犯的错误是觉得：

Kubernetes 要学、Rust 要学、LLM 要学、React 要学、Flutter 要学、云原生要学……

结果每个都懂一点，没有任何一个真正能用。

真正有前瞻性的人反而非常善于说：

“我知道这个东西存在，但现在不学。”

Thoughtworks 很多年一直就在用 Technology Radar 这种思路观察技术：不是简单做“热门技术排行榜”，而是区分哪些应该采用、试验、评估。你完全可以做一个自己的技术雷达。

信息源也不要靠“等别人告诉你”

可以建立三层信息源

第一层是弱信号源，用来发现“最近大家在折腾什么”：

GitHub Trending、GitHub Explore、Hacker News、Reddit 的编程社区、X 上你认可的工程师，以及一些技术 Newsletter。

不需要认真学，只需要频繁看到关键词。

比如一个月内连续看到

MCP MCP MCP Agent MCP Claude Code MCP Server

你的大脑就应该亮灯：

“这个东西可能值得进入 Assess。”

第二层是趋势验证源

例如 GitHub Octoverse、Thoughtworks Technology Radar、CNCF 等。它们能帮助你区分：

“这是 Twitter 上突然火了两周”

和

“整个行业真的在迁移。”

例如在 GitHub 2025 的数据里，生成式 AI 已经不是少数人的实验：AI 相关仓库超过 430 万，超过 110 万公共仓库已经在使用 LLM SDK；GitHub 自己把 AI/Agent 工作流描述为逐渐进入普通工程实践。

第三层才是深度学习源

官方文档、GitHub README、源码、架构文档、conference talk。

也就是说：

社交媒体负责“发现”，
报告负责“判断”，
官方资料负责“学习”。

不要反过来。

还有一个非常重要的能力：学会看“连接”

很多初学者会有这样的疑问：：

“各种平台之间如何协作。”

这其实是非常好的问题。

很多人学习计算机时，脑子里是：

每一门都是孤岛。

但实际软件世界更像：

再进入现在的 AI 开发:

所以以后学一个东西，强迫自己回答五个问题：

  1. 它解决什么问题？
  2. 它的输入是什么？
  3. 它的输出是什么？
  4. 它上游是谁？
  5. 它下游是谁？

你的知识就会开始从“知识点”变成“系统”。

而系统思维本身就是前瞻性的重要来源。

学习方式应该从“开始学”转到“开始做“

不要今天学 Docker 教程,明天学 Redis 教程,后天学 Next.js 教程

而是每隔一段时间做一个完整的小产品。

例如：

“做一个 AI 学习助手。”

然后逼自己经历:

做到某一步，自然会问：

“有没有更好的部署方法？”

然后可能发现 Vercel / Railway / Fly.io / Cloudflare。

做到另一处：

“AI 怎么访问我的数据库或者 GitHub？”

自然会碰到 tool calling / MCP / agent。

这种发现方式比刷：

《2026程序员必须掌握的50个工具》

有效很多。

因为你的知识是长在问题上的。

AI 时代还有一个变化值得特别注意

以后优秀工程师与普通工程师之间的区别，可能越来越不是：

谁写代码写得快。

而是：

谁能定义问题、拆任务、选择工具、组合系统、验证结果。

GitHub 对高级 AI 工具用户的研究也出现了类似趋势：开发者的工作开始更多转向 理解工作（understanding）、指导工作（directing）、验证工作（verifying）。

所以千万不要因为 AI 能写代码就觉得：

“那我还学数据结构、OS、网络干嘛？”

恰恰相反。

AI 可以很容易给你一些代码，但是如果不了解相应的知识，可能根本无法判断它写得对不对

基础知识决定你的判断上限，新工具决定你的执行速度
